# 1. Arquitectura que vamos a utilizar

La solución tendrá cuatro proyectos:

```text
HVAC.Api
HVAC.Application
HVAC.Domain
HVAC.Infrastructure
```

Visualmente:

```text
                    ┌──────────────────────┐
                    │       HVAC.Api       │
                    │ Controllers          │
                    │ Middleware           │
                    │ DI / Program.cs      │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │  HVAC.Application    │
                    │ Use Cases            │
                    │ DTOs                 │
                    │ Interfaces           │
                    │ Validators           │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │     HVAC.Domain      │
                    │ Entities             │
                    │ Value Objects        │
                    │ Enums                │
                    │ Domain Exceptions    │
                    │ Domain Rules         │
                    └──────────────────────┘
                               ▲
                               │
                    ┌──────────┴───────────┐
                    │  HVAC.Infrastructure │
                    │ EF Core              │
                    │ PostgreSQL           │
                    │ Repositories         │
                    │ External services    │
                    └──────────────────────┘
```

La regla fundamental será:

```text
Api
 ↓
Application
 ↓
Domain

Infrastructure
 ↓
Application
 ↓
Domain
```

Es decir:

**Domain**

**No conoce a nadie.**

```text
Domain
  └── ninguna dependencia externa
```

**Application**

Conoce únicamente:

```text
Application → Domain
```

**Infrastructure**

Puede conocer:

```text
Infrastructure → Application
Infrastructure → Domain
```

**Api**

Conoce:

```text
Api → Application
```

Y normalmente evitaremos que `Api` dependa directamente de `Infrastructure` en el código de negocio, aunque `Program.cs` tendrá que registrar las implementaciones de infraestructura mediante DI.

---

# 2. ¿Por qué cuatro proyectos?

Porque cada capa tiene una responsabilidad diferente.

## Domain

Representa el **negocio**.

Por ejemplo:

```text
Una orden de trabajo no puede cerrarse
si todavía tiene actividades pendientes.
```

Eso es una regla de negocio.

No debería estar en:

```text
Controller
DbContext
SQL
DTO
```

Debe vivir en el dominio.

---

## Application

Representa los **casos de uso**.

Por ejemplo:

```text
Crear orden de trabajo
Consultar orden
Asignar técnico
Iniciar mantenimiento
Finalizar mantenimiento
Cerrar orden
```

Application coordina el caso de uso.

---

## Infrastructure

Se ocupa de detalles técnicos:

```text
PostgreSQL
EF Core
Email
Storage
GPS
archivos
etc.
```

---

## Api

Es la entrada HTTP:

```http
POST /api/work-orders
GET /api/work-orders/123
```

El controller no debería contener lógica de negocio.

# 4. Agregar referencias

Ahora viene algo **muy importante para entender Clean Architecture**.

### Application → Domain

```bash
dotnet add HVAC.Application reference HVAC.Domain
```

### Infrastructure → Application

```bash
dotnet add HVAC.Infrastructure reference HVAC.Application
```

### Infrastructure → Domain

```bash
dotnet add HVAC.Infrastructure reference HVAC.Domain
```

### Api → Application

```bash
dotnet add HVAC.Api reference HVAC.Application
```

Y para permitir que `Program.cs` registre Infrastructure:

```bash
dotnet add HVAC.Api reference HVAC.Infrastructure
```

Por lo tanto:

```text
HVAC.Domain
      ↑
      │
HVAC.Application
      ↑
      │
   HVAC.Api

HVAC.Domain
      ↑
      │
HVAC.Infrastructure
      ↑
      │
   HVAC.Api
```

Esto último es importante:

> Que `Api` tenga referencia a `Infrastructure` para composición/DI **no significa que Api deba conocer los detalles de EF Core o PostgreSQL en sus controllers**.

# 6. Nuestro primer Aggregate

Aquí entra DDD.

Vamos a tener:

```text
WorkOrder
```

como Aggregate Root.

Una orden podría tener:

```text
WorkOrder
│
├── Id
├── Number
├── CustomerId
├── EquipmentId
├── TechnicianId
├── Status
├── ScheduledDate
└── Activities
```

Y más adelante:

```text
WorkOrder
   │
   ├── WorkOrderActivity
   │       ├── Activity
   │       └── Answers
   │
   └── Photos
```

La idea es que `WorkOrder` controle las modificaciones de su propio estado.

Por ejemplo:

```csharp
workOrder.Start();
```

en lugar de:

```csharp
workOrder.Status = WorkOrderStatus.InProgress;
```

¿Por qué?

Porque el Aggregate debe proteger las reglas del negocio.

# 7. Crear el primer Entity

En:

```text
HVAC.Domain
└── Entities
    └── WorkOrder.cs
```

podríamos comenzar con:

```csharp
namespace HVAC.Domain.Entities;

public sealed class WorkOrder
{
    private WorkOrder()
    {
    }

    private WorkOrder(
        Guid id,
        string number,
        Guid customerId,
        Guid equipmentId)
    {
        Id = id;
        Number = number;
        CustomerId = customerId;
        EquipmentId = equipmentId;
        Status = WorkOrderStatus.Pending;
    }

    public Guid Id { get; private set; }

    public string Number { get; private set; } = null!;

    public Guid CustomerId { get; private set; }

    public Guid EquipmentId { get; private set; }

    public WorkOrderStatus Status { get; private set; }

    public static WorkOrder Create(
        string number,
        Guid customerId,
        Guid equipmentId)
    {
        if (string.IsNullOrWhiteSpace(number))
            throw new ArgumentException(
                "El número de la orden es obligatorio.",
                nameof(number));

        if (customerId == Guid.Empty)
            throw new ArgumentException(
                "El cliente es obligatorio.",
                nameof(customerId));

        if (equipmentId == Guid.Empty)
            throw new ArgumentException(
                "El equipo es obligatorio.",
                nameof(equipmentId));

        return new WorkOrder(
            Guid.NewGuid(),
            number,
            customerId,
            equipmentId);
    }

    public void Start()
    {
        if (Status != WorkOrderStatus.Pending)
            throw new InvalidOperationException(
                "Solo una orden pendiente puede iniciarse.");

        Status = WorkOrderStatus.InProgress;
    }

    public void Complete()
    {
        if (Status != WorkOrderStatus.InProgress)
            throw new InvalidOperationException(
                "Solo una orden en progreso puede completarse.");

        Status = WorkOrderStatus.Completed;
    }
}
```

Aquí ya tenemos algo importante de DDD:

```csharp
public void Start()
```

La entidad tiene comportamiento.

No es simplemente:

```text
Id
Name
Status
...
```

Esto es lo que suele llamarse un **modelo de dominio rico**.

# 9. Una decisión importante

No quiero que hagamos esto:

```csharp
public class WorkOrderService
{
    public void Start(WorkOrder order)
    {
        order.Status = WorkOrderStatus.InProgress;
    }
}
```

porque estaríamos sacando la regla del dominio.

Preferimos:

```csharp
order.Start();
```

El dominio decide si puede iniciarse.

# 13. Repository: una abstracción

Application necesita guardar la orden, pero **no debe saber que usamos PostgreSQL**.

Creamos:

```text
HVAC.Application
└── Abstractions
    └── Persistence
        └── IWorkOrderRepository.cs
```

```csharp
using HVAC.Domain.Entities;

namespace HVAC.Application.Abstractions.Persistence;

public interface IWorkOrderRepository
{
    Task AddAsync(
        WorkOrder workOrder,
        CancellationToken cancellationToken);

    Task<WorkOrder?> GetByIdAsync(
        Guid id,
        CancellationToken cancellationToken);
}
```

Application dice:

> "Necesito guardar una WorkOrder."

Pero no dice:

```text
INSERT INTO work_orders...
```

ni:

```csharp
DbContext
```

ni:

```text
PostgreSQL
```

# 14. Infrastructure implementará el repository

Más adelante tendremos:

```text
HVAC.Infrastructure
└── Persistence
    └── Repositories
        └── WorkOrderRepository.cs
```

```csharp
public sealed class WorkOrderRepository
    : IWorkOrderRepository
{
    private readonly HvacDbContext _context;

    public WorkOrderRepository(HvacDbContext context)
    {
        _context = context;
    }

    public async Task AddAsync(
        WorkOrder workOrder,
        CancellationToken cancellationToken)
    {
        await _context.WorkOrders.AddAsync(
            workOrder,
            cancellationToken);
    }

    public async Task<WorkOrder?> GetByIdAsync(
        Guid id,
        CancellationToken cancellationToken)
    {
        return await _context.WorkOrders
            .FirstOrDefaultAsync(
                x => x.Id == id,
                cancellationToken);
    }
}
```

La implementación conoce EF Core.

El dominio no.

Application tampoco necesita conocer EF Core.

---

# 15. ¿Y quién hace SaveChanges?

Aquí tenemos una decisión arquitectónica importante.

No quiero que cada repository haga:

```csharp
await _context.SaveChangesAsync();
```

porque eso puede dificultar una operación que involucre varias entidades.

Preferimos que Application coordine la transacción mediante una abstracción, por ejemplo:

```csharp
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(
        CancellationToken cancellationToken);
}
```

Y después:

```text
Application
    ↓
IWorkOrderRepository
    ↓
IUnitOfWork
    ↓
Infrastructure
    ↓
EF Core
    ↓
PostgreSQL
```

---

# 16. ¿Necesitamos MediatR?

No necesariamente.

Este punto es importante porque en proyectos .NET se suele hacer:

```text
Controller
 ↓
MediatR
 ↓
Command
 ↓
Handler
```

para absolutamente todo.

DDD + Clean Architecture **no requieren MediatR**.

Podemos comenzar perfectamente con:

```csharp
WorkOrderService
```

o una estructura de casos de uso propia.

Por ejemplo:

```text
Application
└── WorkOrders
    └── Create
        ├── CreateWorkOrderRequest.cs
        └── CreateWorkOrderHandler.cs
```

Y:

```csharp
public sealed class CreateWorkOrderHandler
{
    private readonly IWorkOrderRepository _repository;
    private readonly IUnitOfWork _unitOfWork;

    public CreateWorkOrderHandler(
        IWorkOrderRepository repository,
        IUnitOfWork unitOfWork)
    {
        _repository = repository;
        _unitOfWork = unitOfWork;
    }

    public async Task<Guid> HandleAsync(
        CreateWorkOrderRequest request,
        CancellationToken cancellationToken)
    {
        var workOrder = WorkOrder.Create(
            number: $"OT-{DateTime.UtcNow:yyyyMMddHHmmss}",
            customerId: request.CustomerId,
            equipmentId: request.EquipmentId);

        await _repository.AddAsync(
            workOrder,
            cancellationToken);

        await _unitOfWork.SaveChangesAsync(
            cancellationToken);

        return workOrder.Id;
    }
}
```

Esto es perfectamente válido.

# 17. Controller

Finalmente:

```text
HVAC.Api
└── Controllers
    └── WorkOrdersController.cs
```

```csharp
[ApiController]
[Route("api/work-orders")]
public sealed class WorkOrdersController : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Create(
        CreateWorkOrderRequest request,
        CancellationToken cancellationToken)
    {
        var id = await _handler.HandleAsync(
            request,
            cancellationToken);

        return CreatedAtAction(
            nameof(GetById),
            new { id },
            new { id });
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> GetById(Guid id)
    {
        // ...
        return Ok();
    }
}
```

El controller queda delgado.

No contiene:

```text
Reglas de negocio
SQL
EF Core
Validaciones complejas
Cálculos
```

Simplemente traduce:

```text
HTTP → Application
```

y:

```text
Application → HTTP

```
