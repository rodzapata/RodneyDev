### Paso 2. Evitar consultas SQL demasiado grandes

Actualmente estamos cargando dos colecciones:

- `Activities` con sus `Questions`.
- `Activities` con sus `Answers`.

EF Core puede generar una consulta con múltiples JOIN que multiplique las filas devueltas. Para evitar ese problema, podemos utilizar `AsSplitQuery()`.

Deja el método así:

```csharp

public async Task<WorkOrder?> GetByIdWithDetailsAsync(
    Guid id,
    CancellationToken cancellationToken)
{
    return await _context.WorkOrders
        .AsSplitQuery()
        .Include(x => x.Activities)
            .ThenInclude(x => x.Questions)
        .Include(x => x.Activities)
            .ThenInclude(x => x.Answers)
        .FirstOrDefaultAsync(
            x => x.Id == id,
            cancellationToken);
}

```

¿Qué hace `AsSplitQuery()`?

En lugar de intentar recuperar todo mediante una única consulta SQL con múltiples JOIN, EF Core ejecuta varias consultas relacionadas para cargar las colecciones.

Esto puede reducir la duplicación de datos cuando un agregado tiene varias colecciones.

No significa que siempre sea más rápido: implica más viajes a la base de datos, pero suele ser conveniente para agregados con varias colecciones.

```csharp

using AcSoft.Domain.Entities;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace AcSoft.Infrastructure.Persistence.Configurations;

public sealed class WorkOrderConfiguration
    : IEntityTypeConfiguration<WorkOrder>
{
    public void Configure(EntityTypeBuilder<WorkOrder> builder)
    {
        builder.ToTable("WorkOrders");

        builder.HasKey(x => x.Id);

        builder.Property(x => x.Number)
            .HasMaxLength(30)
            .IsRequired();

        builder.HasIndex(x => x.Number)
            .IsUnique();

        builder.Property(x => x.CustomerId)
            .IsRequired();

        builder.Property(x => x.EquipmentId)
            .IsRequired();

        builder.Property(x => x.Status)
            .IsRequired();

        // Relación con las actividades de la orden.
        builder.HasMany(x => x.Activities)
            .WithOne()
            .HasForeignKey(x => x.WorkOrderId)
            .OnDelete(DeleteBehavior.Cascade);

        builder.Navigation(x => x.Activities)
            .HasField("_activities")
            .UsePropertyAccessMode(PropertyAccessMode.Field);

        // Relación con las asignaciones de técnicos.
        builder.HasMany(x => x.Assignments)
            .WithOne()
            .HasForeignKey(x => x.WorkOrderId)
            .OnDelete(DeleteBehavior.Cascade);

        builder.Navigation(x => x.Assignments)
            .HasField("_assignments")
            .UsePropertyAccessMode(PropertyAccessMode.Field);
    }
}

```

## 2. ¿Por qué configuramos las colecciones de esta manera?

Por ejemplo, en tu entidad tienes:


La propiedad `Activities` devuelve una colección de solo lectura.

Por eso utilizamos:

```csharp

    .HasField("_activities")
```

## 3. Dos decisiones de diseño importantes

Número de orden único

```csharp
builder.HasIndex(x => x.Number).IsUnique();
```

Esto evita que existan dos órdenes con el mismo número. Es importante porque actualmente generas el número utilizando la fecha y hora hasta los segundos. Si se crean dos órdenes en el mismo segundo, podría producirse una colisión.

Más adelante mejoraremos esa generación.

Eliminación en cascada

```csharp
.OnDelete(DeleteBehavior.Cascade);
```

Cuando se elimina una orden, EF Core también elimina sus actividades y asignaciones dependientes.

Esto es una decisión de persistencia, no una autorización para eliminar órdenes históricas desde el negocio. En un sistema de mantenimiento real, normalmente conviene cancelar o archivar órdenes en lugar de eliminarlas.

```csharp

public sealed class WorkOrderAssignment
{
    private WorkOrderAssignment()
    {
    }

    private WorkOrderAssignment(
        Guid id,
        Guid workOrderId,
        Guid technicianId,
        DateTimeOffset assignedAt)
    {
        Id = id;
        WorkOrderId = workOrderId;
        TechnicianId = technicianId;
        AssignedAt = assignedAt;
    }

    public Guid Id { get; private set; }

    public Guid WorkOrderId { get; private set; }

    public Guid TechnicianId { get; private set; }

    public DateTimeOffset AssignedAt { get; private set; }

    public DateTimeOffset? UnassignedAt { get; private set; }

    public AssignmentEndReason? EndReason { get; private set; }

    public bool IsActive => UnassignedAt is null;

    internal static WorkOrderAssignment Create(
        Guid workOrderId,
        Guid technicianId,
        DateTimeOffset assignedAt)
    {
        if (workOrderId == Guid.Empty)
            throw new ArgumentException(
                "La orden de trabajo es obligatoria.",
                nameof(workOrderId));

        if (technicianId == Guid.Empty)
            throw new ArgumentException(
                "El técnico es obligatorio.",
                nameof(technicianId));

        return new WorkOrderAssignment(
            Guid.NewGuid(),
            workOrderId,
            technicianId,
            assignedAt);
    }

    internal void End(
        DateTimeOffset unassignedAt,
        AssignmentEndReason reason)
    {
        if (!IsActive)
            throw new InvalidOperationException(
                "La asignación ya fue finalizada.");

        if (unassignedAt < AssignedAt)
            throw new InvalidOperationException(
                "La fecha de desasignación no puede ser anterior a la asignación.");

        UnassignedAt = unassignedAt;
        EndReason = reason;
    }
}

```
