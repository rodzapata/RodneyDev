Perfecto. Continuemos con el **Paso 3.2: `WorkSession`**. Esta parte es especialmente importante para ACSoft porque resuelve el escenario de que un técnico deje temporalmente una OT y continúe trabajando en otra.

## 1. Primero, diferenciemos tres conceptos

No debemos mezclar:

```text
WorkOrder
    ↓
¿Quién está asignado?
    → WorkOrderAssignment

¿En qué está trabajando realmente?
    → WorkSession

¿Qué actividades ejecutó?
    → WorkOrderActivity
```

Por ejemplo:

```text
OT-001
Carlos asignado
       │
       ├── WorkSession
       │   08:00 → 09:00
       │
       └── WorkSession
           10:30 → 12:00
```

Carlos estuvo asignado a la OT desde las 08:00 hasta las 12:00, pero **no trabajó continuamente** en ella.

Entre 09:00 y 10:30 pudo estar trabajando en OT-002.

---

# 2. ¿Qué es una `WorkSession`?

Una `WorkSession` representa:

> Un período concreto en el que un técnico estuvo trabajando sobre una determinada orden de trabajo.

Por ejemplo:

```text
Técnico: Carlos
OT:      OT-001
Inicio:  08:00
Fin:     09:00
```

Y posteriormente:

```text
Técnico: Carlos
OT:      OT-001
Inicio:  10:30
Fin:     12:00
```

Son **dos sesiones diferentes**.

---

# 3. `WorkSessionType`

Primero necesitamos decidir qué tipo de tiempo estamos registrando.

Yo no utilizaría solamente:

```text
Working / Paused
```

porque "pausado" no explica qué ocurrió.

Por ejemplo:

```text
09:00 → 10:00
Esperando repuesto
```

es diferente de:

```text
09:00 → 10:00
Desplazamiento
```

y diferente de:

```text
09:00 → 10:00
Almuerzo
```

Por eso:

```csharp
namespace HVAC.Domain.Enums;

public enum WorkSessionType
{
    Work = 1,
    Waiting = 2,
    Travel = 3,
    Break = 4
}
```

Aunque hay una consideración importante: **en esta primera versión vamos a concentrarnos en `Work`** y posteriormente ampliaremos el modelo cuando construyamos el registro de tiempos de espera.

# 4. Crear `WorkSession`

La estructura podría quedar:

```text
HVAC.Domain
├── Entities
│   ├── WorkOrder.cs
│   ├── WorkOrderAssignment.cs
│   └── WorkSession.cs
│
├── Enums
│   ├── WorkOrderStatus.cs
│   ├── AssignmentEndReason.cs
│   └── WorkSessionType.cs
```

Código:

```csharp
using HVAC.Domain.Enums;

namespace HVAC.Domain.Entities;

public sealed class WorkSession
{
    private WorkSession()
    {
    }

    private WorkSession(
        Guid id,
        Guid technicianId,
        Guid workOrderId,
        WorkSessionType type,
        DateTimeOffset startedAt)
    {
        Id = id;
        TechnicianId = technicianId;
        WorkOrderId = workOrderId;
        Type = type;
        StartedAt = startedAt;
    }

    public Guid Id { get; private set; }

    public Guid TechnicianId { get; private set; }

    public Guid WorkOrderId { get; private set; }

    public WorkSessionType Type { get; private set; }

    public DateTimeOffset StartedAt { get; private set; }

    public DateTimeOffset? EndedAt { get; private set; }

    public bool IsActive => EndedAt is null;

    public TimeSpan? Duration =>
        EndedAt.HasValue
            ? EndedAt.Value - StartedAt
            : null;

    public static WorkSession Start(
        Guid technicianId,
        Guid workOrderId,
        WorkSessionType type,
        DateTimeOffset startedAt)
    {
        if (technicianId == Guid.Empty)
            throw new ArgumentException(
                "El técnico es obligatorio.",
                nameof(technicianId));

        if (workOrderId == Guid.Empty)
            throw new ArgumentException(
                "La orden de trabajo es obligatoria.",
                nameof(workOrderId));

        return new WorkSession(
            Guid.NewGuid(),
            technicianId,
            workOrderId,
            type,
            startedAt);
    }

    public void End(DateTimeOffset endedAt)
    {
        if (!IsActive)
            throw new InvalidOperationException(
                "La sesión ya ha finalizado.");

        if (endedAt < StartedAt)
            throw new InvalidOperationException(
                "La fecha de finalización no puede ser anterior al inicio.");

        EndedAt = endedAt;
    }
}
```

# 5. ¿Por qué `WorkSession` no está dentro de `WorkOrder`?

Esta es una decisión importante de DDD.

Podríamos hacer:

```text
WorkOrder
 └── WorkSessions
```

pero no necesariamente es la mejor opción.

Imagina que ACSoft crece y necesitamos:

```text
Technician
 ├── WorkSessions
 ├── Schedule
 ├── Availability
 ├── Location
 ├── Travel
 └── WorkingDay
```

Entonces `WorkOrder` empezaría a controlar demasiadas cosas.

Además, tenemos una regla muy interesante:

> Un técnico no debería tener dos `WorkSession` de tipo `Work` activas simultáneamente.

Esta regla involucra al **técnico**, no solamente a una orden.

Por ejemplo, esto debería ser inválido:

```text
Carlos
│
├── OT-001 → WorkSession activa
│
└── OT-002 → WorkSession activa
```

porque físicamente no puede estar trabajando simultáneamente en dos equipos.

La regla pertenece más naturalmente al contexto de planificación/ejecución del técnico.

# 6. El escenario completo

Ahora podemos representar:

```text
08:00
Carlos
    │
    └── OT-001
        WorkSession
        08:00 → 09:00

09:00
OT-001
    ↓
Waiting

Carlos
    ↓
OT-002

WorkSession
09:00 → 10:30

10:30
Carlos
    ↓
OT-001

WorkSession
10:30 → 12:00

12:00
OT-001
    ↓
Completed
```

Tenemos entonces:

### OT-001

```text
Assignment
Carlos
08:00 → 12:00

WorkSessions

08:00 → 09:00
10:30 → 12:00
```

Tiempo efectivo:

```text
1 hora + 1.5 horas
= 2.5 horas
```

### OT-002

```text
Assignment
Carlos
09:00 → 10:30

WorkSession
09:00 → 10:30
```

Tiempo efectivo:

```text
1.5 horas
```

# 7. Pero hay otra cuestión importante

¿Qué sucede si Carlos está esperando un repuesto?

Tenemos:

```text
08:00 → 09:00  Work
09:00 → 11:00  Waiting
11:00 → 12:00  Work
```

No deberíamos contabilizar:

```text
4 horas trabajadas
```

sino:

```text
Trabajo efectivo = 2 horas
Espera            = 2 horas
Tiempo total      = 4 horas
```

Por eso `WorkSessionType` nos resulta útil.

Podríamos tener:

```text
WorkSession
├── Work
├── Waiting
├── Travel
└── Break
```

Más adelante podremos agregar el motivo de espera:

```csharp
public enum WaitingReason
{
    Customer = 1,
    SparePart = 2,
    Authorization = 3,
    EquipmentShutdown = 4,
    Weather = 5,
    Other = 99
}
```

Pero **no lo agregaría todavía a `WorkSession`** hasta que terminemos de definir el comportamiento.

# 8. ¿Quién crea una `WorkSession`?

Aquí entramos en Application.

No queremos que el Controller haga:

```csharp
new WorkSession(...);
```

La API recibirá algo como:

```http
POST /api/work-orders/{id}/start
```

y Application ejecutará algo conceptualmente parecido a:

```csharp
workOrder.Start();

var session = WorkSession.Start(
    technicianId,
    workOrder.Id,
    WorkSessionType.Work,
    DateTimeOffset.UtcNow);

await repository.AddAsync(session);
await unitOfWork.SaveChangesAsync(cancellationToken);
```

Posteriormente veremos exactamente cómo organizar esto sin MediatR.

# 9. Hay una regla que debemos introducir

Supongamos:

```text
Carlos

09:00 → OT-001
10:00 → OT-002
```

Cuando Carlos intenta comenzar OT-002:

```csharp
WorkSession.Start(...)
```

deberíamos comprobar:

> ¿Carlos ya tiene una sesión de trabajo activa?

Si sí:

```text
❌ No puede comenzar otra.
```

Pero cuidado: esto **no significa que Carlos solamente pueda tener una OT asignada**.

Puede tener:

```text
Carlos

OT-001 → Waiting
OT-002 → Assigned
OT-003 → Assigned
```

y solamente:

```text
OT-002 → WorkSession activa
```

Esto encaja perfectamente con el escenario que planteaste originalmente.

# 10. Nuestro modelo hasta ahora

Estamos llegando a algo así:

```text
                 WORK ORDER
                     │
          ┌──────────┴──────────┐
          │                     │
          ▼                     ▼
 WorkOrderAssignment      WorkOrderActivity
          │                     │
          │                     ▼
          │                ActivityAnswer
          │
          ▼
      Technician
          │
          ▼
     WorkSession
```

Y conceptualmente:

```text
WorkOrderAssignment
    = quién está/estuvo asignado

WorkSession
    = cuándo realmente trabajó

WorkOrderActivity
    = qué actividad ejecutó

ActivityAnswer
    = qué resultado obtuvo
```

Esta separación es **muy importante para ACSoft**.

## Siguiente paso: cerrar el ciclo de `WorkSession`

Antes de pasar a Value Objects, yo haría una pequeña mejora adicional: crear un **`Technician` Aggregate Root** y definir allí la regla:

> Un técnico puede tener varias órdenes asignadas, pero solamente una sesión de trabajo activa.

Después podremos conectar:

```text
Assign → Start Work → Pause/Waiting → Work another OT → Resume → Complete
```

y ahí sí tendremos un modelo bastante sólido para el flujo real de los técnicos de ACSoft.
