## 2. Paso 1: clases y objetos

### 2.1. ¿Qué es una clase?

Una clase es una definición que establece qué datos y comportamientos tendrán los objetos de un determinado tipo.

En AcSoft podemos tener una clase `WorkOrder`, que represente una orden de trabajo.

Una orden puede tener:

* Un identificador.

* Un número de orden.

* Un cliente.

* Un equipo de aire acondicionado.

* Un estado.

* Operaciones para asignar un técnico o iniciar el mantenimiento.

Un objeto es una instancia concreta de esa clase.

Por ejemplo:

* `OT-20261002-001`: mantenimiento de un minisplit.

* `OT-20261002-002`: mantenimiento de una unidad paquete.

Ambas órdenes pueden crearse a partir de la misma clase `WorkOrder`, pero cada una tendrá sus propios datos.


### 2.2. Primer ejemplo: un diseño problemático

Imagina que comenzamos a desarrollar AcSoft de esta manera:

C#

```
public class WorkOrder
{
    public Guid Id { get; set; }

    public string Number { get; set; } = string.Empty;

    public Guid CustomerId { get; set; }

    public Guid EquipmentId { get; set; }

    public string Status { get; set; } = "Pendiente";
}
```

A primera vista parece correcto. Sin embargo, hay varios problemas.

Problema 1: cualquier código puede modificar la orden.

C#

```
var order = new WorkOrder();

order.Status = "Finalizada";
order.Status = "Cualquier cosa";
order.CustomerId = Guid.Empty;
```

El compilador permite estas asignaciones, aunque puedan representar situaciones incorrectas para el negocio.

Problema 2: el estado es un texto libre.

Podemos escribir `"Pendiente"`, `"pendiente"`, `"Finalizada"` o `"Finalizda"`. El compilador no conoce los estados válidos del negocio.

Problema 3: la clase solamente almacena datos.

No define qué significa iniciar una orden, asignar un técnico o finalizar un mantenimiento. La lógica termina dispersándose en controladores y servicios.

Este tipo de diseño se puede utilizar para transportar datos, pero no es suficiente como modelo de dominio si queremos proteger las reglas del negocio.

## 3. Mejorando el diseño con POO

Vamos a aplicar tres conceptos:

1. Estado: los datos que necesita la orden.

2. Comportamiento: las operaciones que puede realizar.

3. Reglas de negocio: las condiciones que deben cumplirse para permitir esas operaciones.

### 3.1. Crear un enumerado para el estado

En lugar de guardar el estado como texto, podemos definir un `enum`.

C#

```
namespace AcSoft.Domain.WorkOrders;

public enum WorkOrderStatus
{
    Pending,
    InProgress,
    Waiting,
    Completed,
    Cancelled
}
```

Ahora el código utiliza valores definidos por el programa:

C#

```
WorkOrderStatus status = WorkOrderStatus.Pending;
```

Esto reduce los errores tipográficos y facilita las comparaciones.

Importante: el `enum` define los estados disponibles, pero no impide por sí solo que una orden pase directamente de `Pending` a `Completed`. Esa regla debe implementarse en el comportamiento de la entidad.

### 3.2. Encapsular la clase `WorkOrder`

Esta es una versión didáctica que introduce los conceptos de POO. En los siguientes pasos podremos adaptarla al código real que ya tienes en AcSoft.

C#

```
namespace AcSoft.Domain.WorkOrders;

public sealed class WorkOrder
{
    public Guid Id { get; private set; }

    public string Number { get; private set; }

    public Guid CustomerId { get; private set; }

    public Guid EquipmentId { get; private set; }

    public WorkOrderStatus Status { get; private set; }

    private WorkOrder(
        string number,
        Guid customerId,
        Guid equipmentId)
    {
        Id = Guid.NewGuid();
        Number = number;
        CustomerId = customerId;
        EquipmentId = equipmentId;
        Status = WorkOrderStatus.Pending;
    }

    public static WorkOrder Create(
        string number,
        Guid customerId,
        Guid equipmentId)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(number);

        if (customerId == Guid.Empty)
            throw new ArgumentException(
                "El cliente es obligatorio.",
                nameof(customerId));

        if (equipmentId == Guid.Empty)
            throw new ArgumentException(
                "El equipo es obligatorio.",
                nameof(equipmentId));

        return new WorkOrder(
            number,
            customerId,
            equipmentId);
    }

    public void Start()
    {
        if (Status != WorkOrderStatus.Pending)
        {
            throw new InvalidOperationException(
                "Solo se puede iniciar una orden pendiente.");
        }

        Status = WorkOrderStatus.InProgress;
    }

    public void Complete()
    {
        if (Status != WorkOrderStatus.InProgress)
        {
            throw new InvalidOperationException(
                "Solo se puede completar una orden en proceso.");
        }

        Status = WorkOrderStatus.Completed;
    }
}
```

Nota: este ejemplo utiliza un constructor privado y una fábrica estática, igual que el enfoque que venimos trabajando para AcSoft. Los métodos Start y Complete son una primera aproximación a las reglas del dominio, no todavía el modelo completo de una orden de mantenimiento.

### 3.3. ¿Qué conceptos de POO acabamos de aplicar?

Encapsulación

`private set`

Desde el exterior podemos consultar el estado de la orden, pero no modificarlo directamente.

Control de construcción

Constructor privado y `Create()`

La creación pasa por una operación que valida los datos obligatorios.

Comportamiento

`Start()` y `Complete()`

La propia orden decide si una transición de estado está permitida.

Validación del dominio

Excepciones ante operaciones inválidas

El objeto no acepta una transición que incumpla las reglas que hemos definido.

## 4. Crear y utilizar objetos de AcSoft

Veamos cómo se utiliza esta clase desde un código de aplicación.

C#

```
using AcSoft.Domain.WorkOrders;

Guid customerId = Guid.NewGuid();
Guid equipmentId = Guid.NewGuid();

WorkOrder order = WorkOrder.Create(
    number: "OT-20261002-001",
    customerId: customerId,
    equipmentId: equipmentId);

Console.WriteLine(order.Number);
Console.WriteLine(order.Status);

// Iniciar el mantenimiento.
order.Start();

Console.WriteLine(order.Status);

// Completar el mantenimiento.
order.Complete();

Console.WriteLine(order.Status);
```

El resultado conceptual sería:

```
OT-20261002-001
Pending
InProgress
Completed
```

Observa que no hemos hecho esto:

C#

```
order.Status = WorkOrderStatus.Completed;
```

Esa asignación no compila porque `Status` tiene un setter privado. Para cambiar el estado, debemos invocar una operación de la entidad que aplique sus reglas.

Esta es una de las ideas centrales de la POO aplicada a DDD: un objeto del dominio no debería ser únicamente una bolsa de propiedades; también debe proteger las reglas que le corresponden.
